## 三、状态管理与数据流

### F2. 设置项散落 + 直读 localStorage 无校验 🟠

**现状**：[App.tsx:36-50](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/App.tsx#L36-L50) 用 `Number(localStorage.getItem(...)) || 3`、`(localStorage.getItem(...) as CardDisplayMode) || "default"` 初始化 5 个设置；[App.tsx:86-110](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/App.tsx#L86-L110) 有 5 段几乎一样的「setX + localStorage.setItem」。PaperView、UserRail 又各自读写自己的键。

**影响**：无校验（脏值/旧值会静默落到 `as` 断言的类型上）；多标签页不同步；逻辑重复。

**解决方案**：抽 `useLocalStorageState<T>(key, parse, fallback)` 通用 hook（含校验 + `storage` 事件跨标签同步），或用轻量 store（Zustand）集中「偏好设置」切片。

```typescript
function useLocalStorageState<T>(key: string, parse: (raw: string) => T, fallback: T) {
  const [val, setVal] = useState<T>(() => {
    try { const r = localStorage.getItem(key); return r != null ? parse(r) : fallback; }
    catch { return fallback; }
  });
  const set = (v: T) => { setVal(v); localStorage.setItem(key, String(v)); };
  useEffect(() => {
    const on = (e: StorageEvent) => { if (e.key === key && e.newValue != null) setVal(parse(e.newValue)); };
    addEventListener("storage", on); return () => removeEventListener("storage", on);
  }, [key]);
  return [val, set] as const;
}
```

### F4. 无乐观更新，Mutation 一律全量刷新 🟠

**现状**：[queries.ts:32](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/hooks/queries.ts#L32) 所有任务变更 `onSuccess: () => invalidateQueries(["tasks"])`，触发整表重新拉取。拖拽、状态切换等高频操作要等一次网络往返才更新 UI。

**影响**：交互有延迟感；拖拽后卡片会「跳一下」；数据量大时刷新成本高。

**解决方案**：对高频 mutation（drag / setStatus）用乐观更新，失败回滚。

```typescript
const drag = useMutation({
  mutationFn: ...,
  onMutate: async (vars) => {
    await qc.cancelQueries({ queryKey: ["tasks"] });
    const prev = qc.getQueryData(["tasks", params]);
    qc.setQueryData(["tasks", params], (old) => applyDragLocally(old, vars));
    return { prev };
  },
  onError: (_e, _v, ctx) => qc.setQueryData(["tasks", params], ctx?.prev),
  onSettled: () => qc.invalidateQueries({ queryKey: ["tasks"] }),
});
```

### F3. 过滤真相分散 🟠

**现状**：`parseSearch` 前后端各一份（见后端文档 B2）；此外前端还在 [App.tsx:112-118](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/App.tsx#L112-L118) 用 `selectedTypes` 二次客户端过滤，而 tag/status/text 走后端。过滤逻辑一半在服务端一半在客户端。

**影响**：同一「可见任务集」由两处拼出，行为难推理；类型 chip 过滤与后端 `type:` 搜索语义不统一。

**解决方案**：明确「服务端为唯一过滤真相」，`selectedTypes` 也转成查询参数交后端处理；前端仅负责展示态（chip 高亮/计数）。短期至少集中到一个 `useVisibleTasks` selector，避免过滤散落在多个 useMemo。

## 四、健壮性与鉴权

### F5. 无 ErrorBoundary + Mutation 失败静默 🔴

**现状**：全项目无 React ErrorBoundary；[queries.ts](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/hooks/queries.ts) 所有 mutation 只有 `onSuccess`，无 `onError`。如 [CalendarView.tsx:104](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/components/CalendarView.tsx#L104) `drag.mutate(...)` 失败时无任何提示，用户以为拖成功了实际没保存。

**影响**：渲染异常会白屏；写操作失败无反馈 → 数据「假成功」，用户困惑。

**解决方案**：
1. 顶层包 `<ErrorBoundary>`（降级 UI + 重载按钮）。
2. 建全局 toast，`QueryClient` 配 `MutationCache({ onError })` 统一兜底提示；关键写操作再补局部 onError 回滚。

---

### F7. 会话中途 401 无全局处理 🔴

**现状**：[auth.tsx:26-32](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/store/auth.tsx#L26-L32) 仅启动时 `api.me()` 决定登录态；[client.ts:15](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/api/client.ts#L15) 遇 401 只是 throw。token 过期后（7 天）用户继续操作，各 Query 报错但 `auth.user` 仍为已登录，不会跳登录页。用户状态还分散在 auth Context（`user`）与 React Query（`useUsers`）两处缓存。

**影响**：登录过期后界面卡在「请求失败」而非引导重登；双缓存易不一致。

**解决方案**：
- 在 `req()` 中拦截 401 → 触发全局登出事件（清 auth + `queryClient.clear()` + 跳 Login）。
- 把当前用户也纳入 React Query（`useQuery(["me"])`）作为单一来源，auth Context 只做薄封装。

### F8. 可访问性缺失 🟠

**现状**：日历格子/卡片用 `<div onClick>`（[CalendarView.tsx:360-367](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/components/CalendarView.tsx#L360)）非按钮；大量纯 emoji 按钮（🔗/🤖/✕）无 `aria-label`；弹层（TaskDrawer/AIPanel/TagCloud）无 `role="dialog"`、无 focus trap，且各自重复 `window.addEventListener("keydown", Esc)`。

**影响**：键盘/读屏不可用；Tab 焦点会漏到弹层背后。

**解决方案**：交互元素用 `<button>`；emoji 按钮补 `aria-label`；抽统一 `<Modal>`（`role="dialog"` + `aria-modal` + focus trap + 集中 Esc/遮罩关闭），替换各弹层重复实现。

## 五、性能与工程化（多为天花板提示）

### F9. 渲染性能 🟡

**现状**：[CalendarView.tsx:58](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/components/CalendarView.tsx#L58) `new Map(...)` 每次渲染重建 typeMap；`WeekRow` 等子组件未 `React.memo`；甘特打包/分组在渲染期做。5 人小数据无碍。

**解决方案**：typeMap 用 `useMemo`；重组件 `memo` + 稳定 props；数据量增大时对 `WeekRow` 做虚拟化。

### F13. AIPanel 绕过 api client 🟡

**现状**：[AIPanel.tsx:84-114](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/components/AIPanel.tsx#L84-L114) 直接 `fetch` 并手写 SSE 解析，脱离统一的 [client.ts](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/api/client.ts) 错误处理；无超时、无重连。

**解决方案**：在 api client 暴露 `streamAnalyze(params, onDelta, signal)`，把 SSE 解析收敛进去，统一错误/超时处理。

### F10. 类型安全 🟠

**现状**：`localStorage.getItem(...) as CardDisplayMode`（[App.tsx:40](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/App.tsx#L40)）等强转无校验；`ext_fields: Record<string, unknown>`（[types.ts:52](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/types.ts#L52)）；`params as Record<string,string|undefined>`（[queries.ts:25](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/hooks/queries.ts#L25)）。

**解决方案**：用运行时校验（zod / 手写 guard）解析 localStorage 与 API 响应；`ext_fields` 定义已知子结构（如 `{ tags?: string[] }`）。

### F14. 无 Lint/CI + 无代码分割 🟡

**现状**：[package.json](file:///Users/wangboyun/workspace/CalendarRecord/frontend/package.json) 无 eslint/prettier 依赖与脚本；无 `.github` CI；`react-markdown`+`remark-gfm` 等重依赖未懒加载，PaperView/AIPanel 全进主包。

**解决方案**：接入 ESLint(typescript-eslint)+Prettier 并加 `lint` 脚本；`React.lazy` 懒加载 PaperView / AIPanel / TagCloud / TypeManager 等按需弹层；配 CI 跑 `tsc + lint + test + build`。
