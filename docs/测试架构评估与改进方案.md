## 二、覆盖结构与回归防线

### T1. 测试倒金字塔缺失 🔴

**现状**：全仓仅两支测试，且都是「输入→输出」的纯函数单测：
- [backend/tests/test_logic.py](file:///Users/wangboyun/workspace/CalendarRecord/backend/tests/test_logic.py)（19 例）——覆盖 `is_delayed / parse_search / apply_drag / build_date_range / can_register / truncate_conclusion / cycle_status`。
- [frontend/src/lib/logic.test.ts](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/lib/logic.test.ts)（14 例）——覆盖 `isDelayed / truncateConclusion / cycleStatus / parseSearch`。

系统里**逻辑最重、最易出错**的部分恰恰零覆盖：CalendarView 手写指针拖拽（`cellW=700` 魔数、边缘换算）、PaperView 就地编辑与版序、TaskDrawer 表单、所有 FastAPI 路由。

**影响**：测试只能证明「纯算子没写错」，不能证明「功能是对的」。任何路由/组件重构都没有护栏，回归全靠人工浏览器复测。

**解决方案**：补齐金字塔中层与顶层（详见 T2/T5/T9），并把 `logic.ts` 中现漏测的纯函数补齐：`normalizeTags`（trim/去重/16 字/10 个上限）、`tagColor`（hash 稳定色）、`getTaskTags`、`getDayMark`（节假日/调休）。

```ts
// frontend/src/lib/logic.test.ts 追加
import { normalizeTags } from "./logic";

describe("normalizeTags", () => {
  it("去重 / 去空白 / 截断超长 / 限制数量", () => {
    expect(normalizeTags([" a ", "a", "", "b"])).toEqual(["a", "b"]);
    expect(normalizeTags(["x".repeat(30)])[0].length).toBe(16);
    expect(normalizeTags(Array.from({ length: 20 }, (_, i) => `t${i}`)).length).toBe(10);
  });
});
```

### T3. 已知真 bug 无回归测试 🔴

**现状**：后端评估已定位真 bug——[ai.py](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/ai.py) 的 `_query_context_tasks` 仅按 `status + text` 过滤上下文，**遗漏 `type` 与 `tag`**（见后端方案 B1）。当前无任何测试能发现它，修复后也无测试防止再次回退。

**影响**：AI 分析的"当前筛选数据"与界面所见不一致，属静默正确性缺陷；缺回归测试意味着修好了也守不住。

**解决方案**：修复的同时补一条接口回归测试，断言 `type:`/`tag:` 筛选真正收窄了送入 LLM 的上下文（配合 T2 的 TestClient 基建，对 `_query_context_tasks` 做直测或对 `/api/ai/analyze` 的上下文构造做断言）。

```python
# backend/tests/test_ai_context.py
def test_context_respects_type_and_tag(db_session, seed_tasks):
    from app.routers.ai import _query_context_tasks
    got = _query_context_tasks(db_session, owner_id=1, q="tag:重点 type:plan")
    assert all("重点" in t.ext_fields.get("tags", []) for t in got)
    assert all(t.type.name == "plan" for t in got)
```

## 三、接口层与测试基建

### T2. 无 API / router 层测试 🔴

**现状**：`backend/tests/` 下**只有** `test_logic.py`，无一支测试触达 FastAPI 路由。这意味着以下"硬约束"目前只有代码、没有验证：
- 数据隔离：`owner_id` 过滤、`_get_owned_task` / `_owned_attachment` / `_get_owned_type` 归属校验（越权返回 404/403）。
- 鉴权：未登录访问受保护接口应 401；[auth.py](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/auth.py) 注册人数上限 `< 5`。
- 业务规则：状态三循环、拖拽改期计数、`done` 切走清空 `actual_done_at`（后端 B5）、`type_id` 归属（后端 B3）。

**影响**：安全与隔离是本系统最关键的正确性要求，却完全无自动化保障；[测试方案.md](file:///Users/wangboyun/workspace/CalendarRecord/docs/测试方案.md) 中相关项只能标"设计保证"，无法转为"已测通过"。

**解决方案**：引入 `httpx` + FastAPI `TestClient`，建立以「独立用户越权」为核心的接口测试套件。

```python
# backend/tests/test_isolation.py
def test_user_cannot_read_others_task(client, user_a, user_b):
    tid = client.post("/api/tasks", json={"title": "私密"}, cookies=user_a).json()["id"]
    r = client.get(f"/api/tasks/{tid}", cookies=user_b)
    assert r.status_code == 404          # 越权不可见

def test_requires_auth(client):
    assert client.get("/api/tasks").status_code == 401

def test_register_capped_at_5(client):
    # 已有 5 个用户时注册应被拒
    assert client.post("/api/auth/register", json={...}).status_code == 400
```

### T4. 无测试 DB fixture / 隔离基建 🟠

**现状**：仓库无 `conftest.py`、无 `pytest.ini` / `pyproject.toml` 的 pytest 配置段；`test_logic.py` 因为是纯函数才无需数据库。一旦上 T2 的接口测试，必须先有"每例独立、可回滚"的数据库与已登录会话夹具。

**影响**：没有地基，接口测试要么打到真实开发库（T10），要么互相污染，无法稳定。

**解决方案**：新增 `backend/tests/conftest.py`——用独立 SQLite（内存或临时文件）+ 依赖覆盖，提供 `client / db_session / user_a / user_b` 夹具。

```python
# backend/tests/conftest.py
import pytest
from fastapi.testclient import TestClient
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from app.main import app
from app.database import Base, get_db

@pytest.fixture
def db_session(tmp_path):
    engine = create_engine(f"sqlite:///{tmp_path/'t.db'}", connect_args={"check_same_thread": False})
    Base.metadata.create_all(engine)
    TestingSession = sessionmaker(bind=engine)
    s = TestingSession()
    try:
        yield s
    finally:
        s.close()

@pytest.fixture
def client(db_session):
    app.dependency_overrides[get_db] = lambda: db_session
    with TestClient(app) as c:
        yield c
    app.dependency_overrides.clear()
```

### T5. 前端无组件测试基建 🟠

**现状**：[vite.config.ts](file:///Users/wangboyun/workspace/CalendarRecord/frontend/vite.config.ts) 只有 `plugins + server.proxy`，**没有 `test` 配置块**（无 `environment: "jsdom"`）；[package.json](file:///Users/wangboyun/workspace/CalendarRecord/frontend/package.json) 依赖里没有 `jsdom` 与 `@testing-library/react`。现有 `logic.test.ts` 只测纯函数，才不需要 DOM。

**影响**：想给 TaskDrawer、TypeChips、TagCloud 等写渲染/交互测试，"开箱即跑不了"，组件层永远测不到。

**解决方案**：补 vitest 的 jsdom 环境与 Testing Library。

```ts
// vite.config.ts —— 追加 test 块
export default defineConfig({
  plugins: [react()],
  server: { /* 略 */ },
  test: {
    environment: "jsdom",
    globals: true,
    setupFiles: "./src/test/setup.ts",
  },
});
```

// package.json devDependencies 追加
"jsdom": "^25",
"@testing-library/react": "^16",
"@testing-library/jest-dom": "^6"

## 四、度量、工程化与一致性

### T6. 无覆盖率度量 🟠

**现状**：`pytest` 与 `vitest` 均未接覆盖率插件；覆盖率靠肉眼估。

**影响**：无法量化"测了多少"，也无法在 CI 上设阈值防止覆盖率倒退。

**解决方案**：后端 `pytest-cov`、前端 `@vitest/coverage-v8`，并对核心目录设最低阈值。

```bash
# 后端
pytest --cov=app --cov-report=term-missing --cov-fail-under=60
# 前端
vitest run --coverage
```

### T7. 无 CI 🟠

**现状**：仓库无 `.github/workflows`（glob 无匹配）。测试是否通过完全依赖开发者本地手动记忆。

**影响**：提交/合并前无强制门禁，回归可以悄悄进主干；[测试方案.md](file:///Users/wangboyun/workspace/CalendarRecord/docs/测试方案.md) 的台账无法被自动核对。

**解决方案**：加一条 GitHub Actions，PR 触发 `tsc -b` + `vitest run` + `pytest`，红则不可合并。

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: cd frontend && npm ci && npm run build && npx vitest run --coverage
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: cd backend && pip install -r requirements.txt && pytest --cov=app
```

### T8. 前后端逻辑对等未强制 🟠

**现状**：`parseSearch` / `isDelayed` / `cycleStatus` 等规则在前端 [logic.ts](file:///Users/wangboyun/workspace/CalendarRecord/frontend/src/lib/logic.ts) 与后端 [logic.py](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/logic.py) 各写一份，各自单测（14 例 vs 19 例）。两份用例并非同一组黄金样本，规则可能悄悄漂移（如 `status:` 大小写、tag 归一化差异）。

**影响**：同一查询在前端过滤与后端过滤结果不一致，属难复现的"数据对不上"类缺陷。

**解决方案**：抽一份语言无关的**黄金用例表**（JSON），前后端各自读同一份做参数化测试，保证同输入同输出。

```json
// tests/fixtures/search_cases.json（前后端共用）
[
  { "q": "status:done type:plan 读源码",
    "statuses": ["done"], "types": ["plan"], "tags": [], "text": "读源码" },
  { "q": "tag:公司A tag:重点 复盘",
    "statuses": [], "types": [], "tags": ["公司A","重点"], "text": "复盘" }
]
```

## 五、端到端与非功能

### T9. 无 E2E 测试 🟠

**现状**：拖拽甘特、卡片就地编辑、图片粘贴上传、AI SSE 流式渲染等最复杂交互，只靠人工浏览器点验（本项目多次"浏览器验证通过"均为一次性手测），无可重复脚本。

**影响**：手测不可回归、易遗漏路径；跨浏览器/移动端响应式尤其难覆盖。

**解决方案**：引入 Playwright，为「登录→建任务→拖拽改期→标记完成→搜索→AI 分析」主流程写少量高价值 E2E，纳入 CI（可 nightly 触发以控时长）。

---

### T10. 测试与真实数据未隔离 🟡

**现状**：后端默认连接开发用 SQLite；一旦接口测试未走独立库（见 T4），将污染真实数据。

**影响**：测试副作用写入真实库；WAL 单写下并发跑测试还可能锁冲突。

**解决方案**：以 T4 的临时库夹具为准，测试**严禁**连默认库；在 conftest 强制 `DATABASE_URL` 指向临时文件，并在 CI 用全新容器/临时目录。

---

### T11. 非功能维度零测试 🟡

**现状**：无性能基准（大数据量下日历/词云渲染）、无可访问性检查（前端 F8 提到的 div 当按钮、无 aria/role=dialog）、无响应式与视觉回归。

**影响**：性能与可用性退化无人察觉；UI 改版易引入视觉回归。

**解决方案**（按需、非阻塞）：Playwright 内置 `toHaveScreenshot` 做关键弹层视觉快照；`axe-core` 做 a11y 断言；对大列表渲染加一条粗粒度性能预算测试。当前规模可延后，先留基建挂点。
