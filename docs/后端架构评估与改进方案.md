## 二、安全类

### A1. JWT 默认密钥可上生产 🔴

**现状**：[config.py:21](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/config.py#L21) 默认 `JWT_SECRET="dev-secret-change-me"`，[docker-compose.yml:7](file:///Users/wangboyun/workspace/CalendarRecord/docker-compose.yml#L7) 兜底值同样是它。无任何启动期校验拒绝默认值。

**影响**：部署时若遗漏 `JWT_SECRET`，攻击者用公开的默认密钥即可伪造任意用户（含 admin）token，等于完全绕过鉴权。

**解决方案**：启动即 fail-fast，非开发环境禁止使用默认/弱密钥。

```python
# config.py
import os
import secrets

class Settings:
    APP_ENV: str = os.getenv("APP_ENV", "dev")  # dev / prod
    JWT_SECRET: str = os.getenv("JWT_SECRET", "dev-secret-change-me")

    def validate(self) -> None:
        weak = {"", "dev-secret-change-me", "change-me", "secret"}
        if self.APP_ENV != "dev":
            if self.JWT_SECRET in weak or len(self.JWT_SECRET) < 32:
                raise RuntimeError(
                    "生产环境必须设置强 JWT_SECRET（≥32 字符）。"
                    f"可用：{secrets.token_urlsafe(48)}"
                )

settings = Settings()
```

```python
# main.py 的 lifespan 内最先调用
settings.validate()
```

同时把 [docker-compose.yml](file:///Users/wangboyun/workspace/CalendarRecord/docker-compose.yml) 的 `JWT_SECRET` 兜底值改为空并在 `.env.example` 里注明必填。

### A2. `ext_fields` / 标签仅前端校验 🔴

**现状**：[schemas.py:92](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/schemas.py#L92) `ext_fields: dict` 全盘接收客户端 JSON；「单标签≤16 字、每任务≤10 个、去重小写」的硬约束只在前端 `normalizeTags` 生效。直接调 API 可写入任意大小、任意结构 JSON。

**影响**：数据完整性被绕过；超大 JSON 造成存储膨胀 / 潜在 DoS；`tag` 过滤依赖的结构（string 数组）可被破坏。

**解决方案**：把标签规范化下沉到后端，作为唯一真相；在写入前统一清洗 `ext_fields`。

```python
# logic.py —— 与前端 normalizeTags 对齐的后端实现（唯一真相）
def normalize_tags(raw) -> list[str]:
    if not isinstance(raw, list):
        return []
    seen, out = set(), []
    for t in raw:
        s = str(t).strip()[:16]
        key = s.lower()
        if s and key not in seen:
            seen.add(key)
            out.append(s)
        if len(out) >= 10:
            break
    return out

def sanitize_ext_fields(ext: dict | None) -> dict:
    ext = dict(ext or {})
    if "tags" in ext:
        ext["tags"] = normalize_tags(ext["tags"])
    return ext
```

在 [tasks.py](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/tasks.py) `create_task` / `update_task` 写入 `ext_fields` 前调用 `sanitize_ext_fields`。并对整体大小设上限（如 JSON 序列化后 > 16KB 直接 400）。

### A3. 上传先全量读入内存 🟠

**现状**：[files.py:47-48](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/files.py#L47-L48) `data = await file.read()` 读完整个文件后才比对 `MAX_SIZE`。

**影响**：超大 body 可打满进程内存。

**解决方案**：分块读取，边读边累计，超限即中断并清理。

```python
CHUNK = 1024 * 1024
async def _save_within_limit(file: UploadFile, path: str, max_size: int) -> int:
    total = 0
    with open(path, "wb") as f:
        while chunk := await file.read(CHUNK):
            total += len(chunk)
            if total > max_size:
                f.close(); os.remove(path)
                raise HTTPException(413, "文件过大（上限 20MB）")
            f.write(chunk)
    return total
```

### A4. 登录无失败限流 🟠

**现状**：[auth.py:52-59](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/auth.py#L52-L59) 无失败计数。argon2 慢哈希可缓解但不足。

**解决方案（轻量）**：基于内存的 IP+用户名滑动窗口计数（单实例足够），或引入 `slowapi`。5 人规模用内存字典即可：

```python
from collections import defaultdict
from time import time

_fails: dict[str, list[float]] = defaultdict(list)

def check_login_rate(key: str, limit=5, window=300):
    now = time()
    _fails[key] = [t for t in _fails[key] if now - t < window]
    if len(_fails[key]) >= limit:
        raise HTTPException(429, "尝试过于频繁，请稍后再试")

def record_login_fail(key: str):
    _fails[key].append(time())
```

登录失败时 `record_login_fail`，成功时清空。

## 三、正确性 / 一致性类

### B1. AI 上下文筛选与列表筛选不一致 🔴（真 bug）

**现状**：列表接口 [tasks.py:68-86](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/tasks.py#L68-L86) 支持 `status / type / tag / 文本` 四维过滤；AI 上下文 [ai.py:69-76](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/ai.py#L69-L76) **只处理 status 与文本，遗漏 type 和 tag**。

**影响**：用户按类型/标签筛选后点「基于当前筛选分析」，AI 实际拿到更宽的数据集，结论失真。

**解决方案**：抽取统一的「任务查询构造器」，列表与 AI 共用，杜绝两处漂移（同时修复 B1 与减轻 B2）。

```python
# tasks_query.py（新增，被 tasks.py 与 ai.py 共用）
def build_task_query(user, db, *, view=None, anchor=None,
                     custom_start=None, custom_end=None, q=None, owner_id=None):
    stmt = select(Task)
    if user.role == "admin":
        if owner_id is not None:
            stmt = stmt.where(Task.owner_id == owner_id)
    else:
        stmt = stmt.where(Task.owner_id == user.id)
    if view:
        start, end = build_date_range(view, anchor or date.today(), custom_start, custom_end)
        stmt = stmt.where(Task.plan_start_date <= end, Task.plan_due_date >= start)
    parsed = parse_search(q) if q else None
    if parsed:
        if parsed["statuses"]:
            stmt = stmt.where(Task.status.in_(parsed["statuses"]))
        if parsed["types"]:
            stmt = stmt.where(Task.type_id.in_(_resolve_type_ids(parsed["types"], user, db) or [-1]))
        if parsed["text"]:
            like = f"%{parsed['text']}%"
            stmt = stmt.where(or_(Task.title.like(like), Task.link.like(like), Task.conclusion.like(like)))
    return stmt, parsed  # tag 过滤仍在取行后用 _task_has_tag 处理
```

`list_tasks` 与 `_query_context_tasks` 均改为调用它。

### B2. 前后端业务逻辑双份实现 🟠

### B3. `type_id` 落库无归属校验 🟠

**现状**：[tasks.py:111](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/tasks.py#L111)（create）与 [tasks.py:143-144](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/tasks.py#L143-L144)（update）直接写入 `type_id`，不校验该类型对当前用户是否可见/存在。

**影响**：用户可把任务关联到他人私有类型 id（越权引用），或指向不存在 id。

**解决方案**：写入前校验 `type_id ∈ {内置} ∪ {本人自定义}`（管理员放宽）。

```python
def _assert_type_visible(type_id: int | None, user: User, db: Session):
    if type_id is None:
        return
    t = db.get(TaskType, type_id)
    if t is None:
        raise HTTPException(400, "类型不存在")
    if user.role != "admin" and not t.is_builtin and t.owner_id != user.id:
        raise HTTPException(403, "无权使用该类型")
```

## 四、架构 / 可维护性类

### C1. 无数据库迁移 🔴

**现状**：[main.py:14](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/main.py#L14) 靠 `Base.metadata.create_all` 建表——**只建不改**。核心表结构变更（加列/改约束）对已上线库不会自动迁移。

**影响**：这是最影响长期演进的缺口。`ext_fields` JSON 缓解了任务字段扩展，但表结构变更没有安全升级路径，只能手工改库或丢库重建。

**解决方案**：引入 Alembic。
1. `pip install alembic` 并 `alembic init migrations`；`env.py` 指向 `Base.metadata` 与 `settings.DATABASE_URL`。
2. 首个 revision 以当前 schema 为基线（`alembic revision --autogenerate -m "baseline"`）。
3. `main.py` 保留 `create_all` 仅用于全新空库首启；生产升级走 `alembic upgrade head`（可在容器启动脚本里执行）。
4. 注意 SQLite 对 `ALTER` 支持有限，Alembic 需开启 `render_as_batch=True`（batch mode）。

### C3. 无日志 / 可观测性 🟠

**现状**：全项目无 logging 配置、无请求日志、无错误上报。

**解决方案**：
- 配置标准 `logging`（JSON 或 key=value 格式），统一在 `main.py` 初始化。
- 加请求中间件记录 method/path/status/耗时；对 5xx 记录堆栈。
- 关键安全事件（登录失败、越权拒绝、注册限流触发）单独打点，便于审计。

### C4. JWT 无法吊销 🟡

**现状**：无状态 JWT + 7 天有效期；[auth.py:62-65](file:///Users/wangboyun/workspace/CalendarRecord/backend/app/routers/auth.py#L62-L65) logout 仅删 cookie，服务端不失效。

**解决方案**（按需）：
- 缩短 access token 有效期 + 引入 refresh token。
- 或在 payload 加 `token_version`，User 表存 `token_version`，改密/登出全设备时自增，`decode` 后比对。5 人规模可延后。
